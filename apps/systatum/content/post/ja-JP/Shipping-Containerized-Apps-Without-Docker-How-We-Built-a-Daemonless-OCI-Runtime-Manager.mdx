これは、Dockerを使わずにコンテナ化したサービスをユーザーのマシンに届けるために、自分たちで小さなランタイムマネージャーを作った話です。ぶつかった壁と、それをどう乗り越えたかをお話しします。

そもそもの話、うちのアプリは長時間動き続けるバックグラウンドサービスを2つ抱えていて、どちらもDockerイメージとして配布しています。でもユーザーは研究者の方々で、システム管理者じゃありません。アプリを使う前にDockerを入れてくださいってお願いするのは、正直ちょっと酷な話です。目指したい体験はシンプルで、tarballを渡して、インストーラーを実行してもらえば終わり、というものでした。そして行き着いた答えは、Dockerよりずっとシンプルな`runc`だったんです。

## コンテナ入門: 実は仕組みはシンプル

なぜ`runc`が正解なのか。それを理解するには、Linuxでコンテナが実際どう動いているかを知っておくのが早道です。コンテナは仮想マシンじゃありません。ハイパーバイザーもエミュレートされたハードウェアも、独立したカーネルもない。コンテナの正体は、ただのLinuxプロセス(かその集まり)が、システムに対して制限された視界の中で動いているだけのものです。その制限を作っているのが、namespace(名前空間)とcgroupというカーネルの2つの機能です。

**namespace**はプロセスから「何が見えるか」を決めるものです。種類はいくつかあって、PID namespaceはプロセスに専用のプロセスツリーを与えるので、コンテナの中のPID 1はホストのPID 1とは無関係になります。mount namespaceは独立したファイルシステムのビューを与えるので、コンテナの中でマウントしたパスをいじってもホストには響きません。UTS namespace(UNIX Time-sharing Systemの略)は専用のホスト名を、IPC namespace(プロセス間通信、inter-process communicationの略)は共有メモリやメッセージキューの隔離を、network namespaceは専用のネットワークスタックを与えてくれます。つまり「コンテナを起動する」というのは、実はこうした真新しいnamespaceの中で、`rootfs`という別のファイルシステムルートを指すプロセスを1つ立ち上げているだけ、ということなんです。

**cgroup**(control group)はプロセスが「何を使えるか」を管理するもので、CPU時間やメモリ、ディスクI/Oに制限をかけられます。

**rootfs**は、Dockerイメージから取り出した、Linuxユーザーランド一式が入ったただのフラットなディレクトリです。コンテナ専用の特別な要素なんて何もなく、中身はただのファイルの集まり。そもそもDockerイメージは、読み取り専用のファイルシステムレイヤーを積み重ねたもの。展開すれば、こういうシンプルなディレクトリになるのも当然なんです。

**OCI仕様**は、これら全部をまとめ上げる標準規格です。Open Container Initiativeが定義しているコンテナバンドルの形式は、`rootfs/`ディレクトリと`config.json`ファイルを持つディレクトリ、というだけのもの。`config.json`には、作るべきnamespace、コンテナにbind-mountするディレクトリ、付与するLinux capability、設定する環境変数、起動時にexecするプロセスなど、コンテナのあるべき姿がまるごと書かれています。ただのJSONファイルですが、コンテナイメージとそれを動かすランタイムの間の完全な契約書というわけです。私たちのアプリが`runc`にコンテナを動かしてもらうため、その場で作っているのもまさにこの`config.json`です。

**runc**は約10MBの、コンテナプロセスを起動するためだけのシンプルな静的アプリです。本当にそれだけ。裏側では適切なnamespaceフラグを付けて`clone(2)`を呼び、cgroup階層を組み立て、マウントを済ませたうえで、最後にコンテナのエントリポイントに`execve(2)`をかけています。

**Docker**は、この`runc`と`containerd`の上に築かれた、もっとずっと大きなシステムです。レジストリからのイメージ取得、イメージレイヤー管理、ネットワークブリッジ、ボリューム管理、クライアントCLIなど、みんなが便利だと思っているあれこれを全部足し込んでいます。

## 私たちのアプローチ

考え方はシンプルです。ディスク上にDockerイメージ相当の`rootfs`があって、正しい`config.json`さえ作れれば、`runc`を直接呼び出せばよく、Dockerなんてまるごと要らなくなります。そもそもDockerが起動してきたコンテナだって、最終的には全部`runc`を経由しているわけですから。`runc`が欲しがるのは`rootfs`と`config.json`だけ。`rootfs`は`docker export`を使えば手に入りますし、`config.json`は`image-config.json`さえあればその場で作れます。この`image-config.json`は`docker inspect`から取ってきたもので、イメージのエントリポイントや環境変数、作業ディレクトリを記録しているだけの単純なファイルです。

そこで私たちは、`keyai`という小さなデーモンを作りました("Key AI"——これらAIコンテナサービスへの「鍵」だから、という洒落です)。Crystalで書いて、ランタイム依存ゼロの約2MBの単一静的バイナリにコンパイルしています。静的バイナリにしただけで、デプロイまわりの面倒事がごっそり消えてなくなりました。

`keyai`の中身は本当にシンプルで、UNIXソケットをlistenして、繋いできたクライアント(私たちの場合はデスクトップアプリだけ)から`start`、`stop`、`status`、`logs`のリクエストを受け取っているだけです。核になっているのは、こういうただのacceptループです:

```rb
server = UNIXServer.new(SOCKET_PATH)
while client = server.accept?
  spawn handle_request(client)  # parse the JSON request, dispatch by action
end
```

各接続は専用のfiberで処理しているので、あるクライアントからの遅い`logs`リクエストが、別のクライアントの`start`を止めてしまうことはありません。

## 実装

インストールすると、アプリのディレクトリはこんな構成になります:

```
/opt/app/
  bin/
    keyai              ← 私たちのCrystal製デーモン
  containers/
    compilation/
      rootfs/          ← 展開済みのDockerイメージファイルシステム
      image-config.json
    inference/
      rootfs/
      image-config.json
```

`keyai`はsystemdでroot権限のまま動かしています。`runc`が自由にnamespaceを管理したりファイルシステムをマウントしたりできるようにするためです。UNIXソケットは`/run/keyai/oci.sock`という固定パスに置いています。ファイルを`0o666`に`chmod`しているので、デスクトップアプリのGUI側は特権なしでも普通に繋げます。(最初は`XDG_RUNTIME_DIR`の下にソケットを置いていました。sudoを要らなくするにはユーザー所有のディレクトリが必要だろう、という理屈だったんですが、これが見事に裏目に出て、後で詳しく話すインシデントの原因になってしまいました。)

GUIがコンテナを起動するときは、このソケット越しにこんなJSONを送ってきます:

```json
{
  "action": "start",
  "container": "which-service-to-start",
  "config": {
    "uid": 1000,
    "gid": 1000,
    "port": 8000,
    "volumes": {
      "datasets": "/home/user/my-data/datasets",
      "models": "/home/user/my-data/models",
      "compilations": "/home/user/my-data/compilations"
    },
    "devices": ["/dev/my_accelerator0", "/dev/my_accelerator1"]
  }
}
```

デーモン側はイメージのconfigとこのリクエストをマージして、完成した`config.json`をバンドルディレクトリに書き出し、`runc run --detach`を実行します。コンテナのログはそのあと`/var/log/keyai/<name>.log`に吐き出され、GUIは同じソケット経由でステータスをポーリングし続けます。

## 直面した課題

作る前は机上ではシンプルに思えたんですが、実際にはLinuxコンテナモデルの細かい部分にあちこち足をすくわれました。

### PTYクラッシュ

これには本当に頭を抱えました。サービスを起動するたびに、新しいターミナルセッションが作れなくなってしまうんです。犯人はdevptsのマウントオプションにあった`ptmxmode`でした。`runc`は`ptmxmode`を見つけると`/dev/ptmx`をセットアップしようとするんですが、これはカーネルが管理しているデバイスノードなので、勝手にunlinkなんてできません。結果、`runc`は`EBUSY`でクラッシュ。ところが解決策は拍子抜けするほど単純で、`ptmxmode`を消すだけでした。`newinstance`付きでPseudo-Terminal Slaveデバイスをマウントしてコンテナに専用のPTS namespaceを与えたら、あとは`/dev/ptmx`をカーネルに任せて、`runc`には触らせないようにすればいいんです。

```json
{
  "destination": "/dev/pts",
  "type": "devpts",
  "source": "devpts",
  "options": ["nosuid", "noexec", "newinstance", "mode=0620", "gid=5"]
}
```

### デバイスの受け渡し、一番の難所

ここが一番の難所でした。「Dockerをただラップしているだけ」なのか「コンテナを本当に理解しているか」の差が、はっきり出た部分です。

問題の前に、Linuxがハードウェアデバイスをどう表現しているかをおさらいしておきます。`/dev`にある各デバイスファイルには、キャラクタデバイスの`c`かブロックデバイスの`b`、どちらかの種別が付いています。キャラクタデバイスはデータをバイト単位で流すタイプで、ターミナルやシリアルポート、カスタムPCIeアクセラレーターなどがこれにあたります。ブロックデバイスは固定サイズのランダムアクセス読み書きをするタイプで、ハードドライブやUSBストレージが該当します。さらに各デバイスには、どのカーネルドライバが持ち主かを示すメジャー番号と、そのインスタンスを特定するマイナー番号が付いています。`ls -l /dev`で見えるのがこれです:

```
crw-rw----  1 root  dialout  188, 0  /dev/ttyUSB0
brw-rw----  1 root  disk       8, 0  /dev/sda
```

`188, 0`や`8, 0`がそのメジャー・マイナー番号です。プロセスがデバイスファイルを開いて`ioctl`を呼ぶと、カーネルはこの番号を見て正しいドライバにルーティングします。この時点でファイルシステム上のパスはもう関係なくて、大事なのは番号だけなんです。

さて、私たちのアプリは、ホスト上で`/dev/my_accelerator0`として見えるカスタムPCIeアクセラレーターを使っています。最初はbind mountで試しました:

```json
{
  "destination": "/dev/my_accelerator0",
  "type": "bind",
  "source": "/dev/my_accelerator0",
  "options": ["bind"]
}
```

コンテナは起動して、デバイスファイルも正しいパスに現れました。でも、そのデバイスへの`ioctl`はことごとく`EFAULT`——「不正なアドレス」——を返してきます。実はこのデバイス、ちゃんとしたキャラクタデバイスノードではなく、ただのファイルシステムのエントリとしてoverlayされていただけだったんです。本物のキャラクタデバイスからのioctlを待っていたカーネルドライバは、ただのファイルシステムオブジェクトを渡されて、当然のように拒否したというわけです。

Dockerの`--device`は、実はデバイスファイルをbind-mountしていません。ホストと同じ種別・メジャー番号・マイナー番号を持つ新しいデバイスノードを、`mknod`でコンテナの中に作っているんです。そうすれば、パスがどうであれ、カーネルはその番号を頼りに直接ドライバへ`ioctl`をルーティングしてくれます。

私たちも同じことをすればよかったわけです。OCI仕様には、まさにこのための`linux.devices`というフィールドがあります。各エントリにパス・種別・メジャー番号・マイナー番号を書いておくと、`runc`がその値を使ってコンテナの中で`mknod`を呼んでくれます。

メジャー・マイナー番号を読み取るには、ホスト側のデバイスパスに対して`stat(2)`を呼び、`st_rdev`をデコードします。Linuxはちょっと変わったエンコーディングを使っていて、8〜19ビット目がメジャー番号、0〜7ビット目と20ビット目以降がマイナー番号です。マイナー番号側の範囲がこんなに広いのは、Linuxが256をはるかに超える数のデバイスインスタンスをサポートしているからです:

```cr
def read_device_info(path : String) : {String, Int32, Int32}?
  stat_buf = uninitialized LibC::Stat
  return nil if LibC.stat(path, pointerof(stat_buf)) != 0
  rdev = stat_buf.st_rdev.to_u64
  dev_type = case stat_buf.st_mode.to_u32 & 0o170000_u32
             when 0o020000_u32 then "c"  # S_IFCHR
             when 0o060000_u32 then "b"  # S_IFBLK
             else return nil
             end
  major = ((rdev >> 8) & 0xfff_u64).to_i32
  minor = ((rdev & 0xff_u64) | ((rdev >> 12) & ~0xff_u64)).to_i32
  {dev_type, major, minor}
end
```

このデーモンはコンテナ起動のたびにこの処理を呼んでいるので、`config.json`のデバイスエントリはいつもホストの実際の状態と一致しています。

ただ、デバイスノードの作り方を直したあとも、コンテナはまだハードウェアにアクセスできませんでした。エラーは何も出ず、ただ静かに失敗するだけ。デバイスファイルはあるし、コンテナも動いているのに、ドライバがうんともすんとも言わないんです。

今度の犯人は、さっき説明したcgroupのデバイスコントローラーでした。cgroup v2では、`config.json`の`linux.resources.devices`フィールドをもとに、`runc`がeBPFのデバイスフィルタープログラムを組み込みます。このフィールドがないと、`runc`はフィルターを一切入れず、コンテナは親cgroupのポリシーをそのまま受け継ぎます。systemdで管理されたシステムだと、親cgroupは大抵ユーザースライスで、そういうスライスは、よく知られた標準デバイス以外は基本的に全部拒否するポリシーを持っているんです。

私たちのカスタムPCIeデバイスは、当然そのallowlistには入っていません。親cgroupのポリシーが、そのデバイスへのopen呼び出しを黙って全部ブロックしていて、コンテナのログには理由らしきものは何一つ出てきませんでした。解決策は、ハードウェアアクセスが必要なコンテナに対して、`linux.resources.devices`に明示的なallow-allエントリを足してやることです:

```json
"resources": {
  "devices": [
    { "allow": true, "access": "rwm" }
  ]
}
```

こうすると`runc`は、継承していた親のポリシーを上書きして、すべてのデバイスアクセスを許可するeBPFプログラムを組み込んでくれます。正しいメジャー・マイナー番号でノードを作る`linux.devices`のエントリと合わせて、ようやくハードウェアに完全にアクセスできるようになりました。

つまり、名前は似ていても`linux.devices`と`linux.resources.devices`は役割がまったく違います。ハードウェアパススルーを動かすには、両方とも正しく書く必要があるんです。前者は`mknod`でデバイスノードそのものを作るもの。後者はcgroupのポリシーで、そこへのアクセスを許可するものです。片方が抜けると壊れ方も変わります。`linux.devices`がなければノードが存在しません。`linux.resources.devices`がなければノードはあるのに、アクセスだけ黙って拒否されます。

### インターネットアクセス

コンテナの中のDNS解決が壊れていました。つまり、インターネットにつながらないということです。これはさすがに困りました。

調べてみると、Dockerイメージには、Docker内部のDNSスタブリゾルバーを指す`/etc/resolv.conf`があらかじめ焼き込まれていました。このIPアドレス、Dockerデーモンが動いているときにしか存在しないんです。ホストネットワーキングを使う`runc`の下では、当然そんなアドレスには届きません。解決策は、ホストのリゾルバー設定を、コンテナ側のコピーの上から読み取り専用でbind mountしてしまうことでした:

```json
{
  "destination": "/etc/resolv.conf",
  "type": "bind",
  "source": "/etc/resolv.conf",
  "options": ["rbind", "ro"]
}
```

`/etc/hosts`にも同じ対応をしています。

### UIDの再マッピングとnoNewPrivileges

うちのコンテナはrootとして起動したあと、entrypointスクリプトが`gosu`を呼んで、サービスをexecする前に設定済みのユーザーUID・GIDまで権限を落としています。ホスト側のファイル所有権をちゃんと尊重するための、よくあるパターンです。これを動かすために、`noNewPrivileges`は`false`に設定しています。

### 再起動後に消えたソケット

ここまでの話は全部リリースされて問題なく動いていました——あるマシンが再起動されるまでは。再起動後、GUIは`keyai`にまったく繋がらなくなりました。`systemctl status keyai`を見ればenabledでrunningだし、デーモン自身のログにもソケットをbindしてlistenしていたとちゃんと書いてある。それなのにGUI側からは、`keyai`なんて一度も起動していないように見えていたんです。

原因は、さっき触れた`XDG_RUNTIME_DIR`の置き場所にありました。`keyai.service`は`local-fs.target`の後にしか順序付けされていなくて、これはブートのかなり早い段階で到達してしまいます。一方の`XDG_RUNTIME_DIR`(`/run/user/<uid>`)は、そもそもブート時点の話じゃありません。ユーザーセッションが始まったときに`systemd-logind`が作る(そして必要なら再マウントもする)、ログインセッションごとのtmpfsです。つまり、`logind`が「本物の」ランタイムディレクトリを用意する前に`keyai`が起動して`/run/user/<uid>/keyai`を作ってしまうことがあるんです。そこにlogindのマウントが乗ってくると、せっかく作ったソケットはその瞬間に覆い隠されてしまいます。デーモンは生きたままで、その(今や見えなくなった)ソケットファイルに繋がっているんですが、以降`/run/user/<uid>/keyai`を見に行くと、空っぽのディレクトリしか見つかりません。GUI側の可用性チェックはただの`fs.existsSync(SOCKET_PATH)`なので、これがまるっと「起動していない」と判定されてしまったわけです。

解決策は、システムレベルのデーモンのソケットを、ログインセッションがライフサイクルを握っているディレクトリに頼るのをやめることでした。RAM上に乗っている`/run`ファイルシステム配下の固定パス、`/run/keyai/oci.sock`に移したことで、ログインのタイミングに関係なく、マシンが起動している間はずっとそこに存在し続けるようになりました。`keyai`はソケットを作ったあとに`0o666`へ`chmod`するので、`XDG_RUNTIME_DIR`に頼らなくても、ローカルの誰でも接続できます。結果として構成もシンプルになり、ブート順序に起因するレースコンディションも完全になくなりました。ここで学んだのは、システムレベルのデーモンはユーザーセッションのリソースに頼るべきじゃない、というシンプルな教訓です。

### 「Permission Denied」に遭遇したrootプロセス

ちょうど同じ頃、あるユーザーから、inferenceコンテナの起動がこんなエラーで失敗すると報告がありました:

```
Error opening file with mode 'w': '/var/log/our-app/inference.log': Permission denied
```

これは最初、かなり困惑させられました。`keyai`は`systemd`の下で常にrootとして動いていて、rootなら`CAP_DAC_OVERRIDE`で普通のファイル権限チェックくらい素通りできるはずだからです。思いつく限りの可能性を全部つぶしていきました——ファイルの所有者とモード(`root:root`、普通の`644`/`755`)、`lsattr`でimmutableフラグの有無(なし)、カーネルログでAppArmorの拒否がないか(なし!)、root-squashのNFSマウントじゃないか(なし!!)。rootとして動いているプロセスで、本当の権限の衝突が起きている証拠は一つも見つかりませんでした。

本当の原因は、このエラーよりもっと手前にありました。再起動のたびにソケットが消えてしまうという(前述の)バグのせいで、そのユーザーはsystemd経由ではなく、自分の一般デスクトップアカウントで手動で`keyai`を起動して、問題を回避していた可能性があったんです。non-rootのそのプロセスは、自分のセッションディレクトリの下に自由に自分のソケットを作れるので、GUIはそれを「利用可能」だと判断してしまいます。でも`/var/log/keyai/*.log`は、以前の、正しくrootとして動いていたセッションからすでに存在していて、`root:root`所有の`644`モードのままだったんです。non-rootのプロセスが、rootが持っている`644`のファイルを書き込みで開けるはずがありません。つまり「permission denied」は、ログディレクトリの権限のバグなんかじゃなく、デーモンが間違ったユーザーとして動いていたことの、ただの症状だったというわけです。

ソケットのレースコンディションを直すことで根本原因はつぶしましたが、それとは別に、ロガーももう少し頑丈にしておきました。`keyai`が何らかの理由でログファイルを開けなかったときは、今では`/tmp/keyai-logs/`の下にある同じ名前のファイルにフォールバックして、そのプロセスが生きている間はずっとそのフォールバック先を使い続けます。書き込みのたびに元のパスへこっそり再挑戦する、なんてことはもうありません。

## まとめ

OCI仕様こそが、本当の意味での抽象化レイヤーです。`Docker`も`Podman`も`containerd`も`nerdctl`も、結局のところは裏でJSONを組み立てて`runc`(あるいは`crun`?)を呼んでいるだけ。`config.json`さえ理解してしまえば、私たちも同じ仲間入りをしたようなものです。正直なところ、個人的には本番環境ではDockerよりも「keyai」の方がずっと気に入っています。おかげでアプリはかなり速くなりました。起動時間は、前の8秒から1秒に短縮されたんです! これはたぶん、表面積の小ささのおかげでしょう。`runc`と、丁寧に作り込んだ`keyai`以外にデーモンはなく、頼るレジストリもなければ、ガベージコレクションが必要なイメージレイヤーもない。コンテナなんて、ただのディスク上のディレクトリなんですから。

Dockerをユーザーに強制できない環境で、コンテナ化されたサービスが必要なアプリを作っている人には、このアーキテクチャは真剣に検討する価値があります。仕様は安定していますし、`runc`も信頼できます。難しいのはただ一つ、本当に大事な`config.json`のフィールドをひと握り理解することだけ。そこさえ押さえてしまえば、あとはただのJSONです。とはいえ、代替となる技術がないわけではありません。たとえばAWS Firecracker——AWS Fargateを支える中核技術でもあります——は、OCIの`config.json`仕様を読み込んでmicroVMを起動できます。ただ、正直なところ、私たちが目指していた「Dockerなしのコンテナランナー」という当初の狙いからすると、ちょっとやり過ぎ(というより方向性自体が違う)ように思えます。
